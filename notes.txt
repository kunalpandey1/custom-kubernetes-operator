Kubernetes Operators: Controller Basics

Operator = custom resource (CRD) + custom controller

What is a controller?
A controller is a forever-running loop that works to make the cluster's actual state match the desired state.
Built-in example: kube-controller-manager, which runs the core controllers (Deployment, ReplicaSet, Node, etc.).
An operator is your own custom controller for your own resource type.
The reconcile loop

for {
    // 1. Observe: fetch the latest state of the resource (desired vs actual)
    // 2. Compare: apply logic to find the difference between desired and actual
    // 3. Act: update/create/delete things to close the gap
}
// ...then loop back to step 1





Step	Function	            What happens
1	    observe()	            Read the current/updated state of the resource
2	    compare()	            Run your logic: what does the spec say vs. what actually exists?
3	    update() / act()	    Take action to move the actual state toward the desired state



Idempotency (the key property)

Running the reconcile logic once or 100 times must give the same end result.
The loop runs repeatedly, and events can be duplicated or missed, so your logic must not blindly "create". It should check first.
Example: if the EC2 instance already exists and matches the spec, do nothing.
Example: EC2 Instance operator
yaml
kind: EC2Instance        # custom resource
spec: ...                # desired state
The user applies an EC2Instance custom resource.
The custom controller sees it and runs the loop: observe, compare, act.
Result: a real EC2 instance gets created in AWS (and kept in sync with the spec).


One-line summary

An operator watches a custom resource and continuously reconciles reality to match what the user declared, using an idempotent observe → compare → act loop.

In controller-runtime (Kubebuilder / Operator SDK), this loop is your Reconcile() function. The framework handles the "forever loop" and event watching, and you write the compare/act logic inside it.




Here's how it maps to your notes:

Observe: r.Get() fetches the EC2Instance CR (desired state), and DescribeInstances checks what actually exists in AWS.
Compare: the switch compares the two. It has no instance yet, the instance has drifted from the spec, or it already matches.
Act: RunInstances creates the instance. The drift case is a TODO, since the fix depends on what you let users change.
Idempotency: the AWS instance ID is saved in Status.InstanceID. A second run sees it and skips creation, so you never get duplicate instances.
The forever loop: it isn't in the code. The manager started by SetupWithManager calls Reconcile() on every event, and RequeueAfter makes it re-check AWS every 60 seconds, because AWS can change outside Kubernetes.

The skeleton also includes a finalizer. Without one, deleting the CR would leave the real EC2 instance running and billing you. The finalizer makes Kubernetes wait until your controller has terminated the instance.

Things to fill in yourself:

The cloudv1 types (Spec.AMI, Spec.InstanceType, Status.InstanceID, Status.State), which Kubebuilder generates from your _types.go.
AWS client setup, including credentials and region.
Drift handling, plus a check for the instance's terminated or shutting-down state, so you don't treat a dead instance as live.

If you're using Kubebuilder, run make manifests generate after editing the types.

Reconcile Loop: Core Rules :- 

The most important question

1. "Is there anything for me to do?" If no, exit immediately.

Every Reconcile run starts with this check. If actual already equals desired, 
return right away without calling any APIs.

2. Golden rule

Only write to the API server (including status updates) when the actual state differs from the desired state.

This is the rule the sad-path diagram broke. 
Writing .status.lastSync on every run changes the 
object, which fires a watch event, which triggers Reconcile again, 
so the loop never settles.

3. Stateless

The controller does not remember what it did last time.
It can crash, restart, and figure out the state of the world from 
scratch just by observing.
Because of this, never rely on in-memory variables between runs. 
Each run re-reads the desired state (.spec) and the actual state (e.g. AWS) 
and decides from there.


4. Idempotent

Running the loop 100 times on a system that is already in 
the desired state results in zero changes after the first check.
Running again doesn't break anything.






Statelessness in your EC2 operator: the controller keeps no memory in the 
process. Whatever it needs to remember lives outside it, in the API server 
(the EC2Instance CR and its .status.instanceId) and in AWS itself. 
That is how the skeleton avoids creating a duplicate instance after a restart.

Service in Kubernetes

A Service gives a group of Pods one stable address that other 
things can use to reach them.

The problem it solves

Pods are temporary. They get created and destroyed, and every new Pod gets a new IP address. If you have 3 nginx Pods, their IPs change whenever one restarts or gets replaced. Nothing can safely hardcode a Pod's IP.

A Service sits in front of the Pods:

Client ──► Service (stable name + IP) ──► Pod 1
                                      ├─► Pod 2
                                      └─► Pod 3
The Service has a fixed IP and a DNS name (e.g. nginx-svc) that never changes.
It load-balances traffic across the healthy Pods behind it.
It finds those Pods using labels, so it keeps working as Pods come and go.

This is the "DNS just works" line from your slide.

Why write a YAML file for it

Because of the declarative approach from your notes: you say what you want, not how. The YAML is the desired state of the Service, and Kubernetes creates and maintains it. You could also run kubectl expose, but a YAML file can be kept in Git, reviewed in a PR, and re-applied (the GitOps point).

Example

apiVersion: v1
kind: Service
metadata:
  name: nginx-svc
spec:
  selector:
    app: nginx        # sends traffic to Pods with this label
  ports:
    - port: 80        # port the Service listens on
      targetPort: 80  # port on the Pod's container
  type: ClusterIP

selector is the key part. It must match the labels on your Pods, or the Service has nothing to send traffic to.

Service types:-
Type	                    Reachable from
ClusterIP (default)	        Only inside the cluster
NodePort	                Outside, via a port on each node
LoadBalancer	            Outside, via a cloud load balancer

Service = a stable address (fixed IP + DNS name) in front of a group of Pods.

A client Pod sends its request to the Service, and the Service forwards it to a destination Pod. The client gets the Pod's response without knowing its IP.
The Service finds its Pods using labels (selector) and load-balances across the healthy ones.
Defined in a YAML file, following the declarative approach (say what, not how).

command to give to do the kubebuilder setup:- 


kubebuilder init \
  --domain cloud.com \
  --repo github.com/kunalpandey1/custom-kubernetes-operator \
  --project-name custom-kubernetes-operator




Think of kubebuilder init like npx create-react-app or git init. It creates the starting skeleton for a new project. At this stage you have no CRD and no controller, only the empty shell that will hold them.

The command answers three questions about your project: what is its domain, where does the code live (repo), and what is it called (project-name).

The three flags
1. --domain cloud.com

Question it answers: "What namespace should my API names live under?"

Every custom resource belongs to an API group, written as <group>.<domain>. The domain makes your group globally unique, so your EC2Instance can't clash with someone else's.

group (you choose later) + domain (you chose now) = full API group
compute                  + cloud.com               = compute.cloud.com

It shows up in your CR's apiVersion:


apiVersion: compute.cloud.com/v1
kind: EC2Instance



Real examples: apps (built-in), cert-manager.io, monitoring.coreos.com. It works like a Java package name (com.company.app).

2. --repo github.com/kunalpandey1/custom-kubernetes-operator

Question it answers: "What is my Go module called?"

This is the Go module path. It's written into go.mod and used in every Go import inside your project:


import computev1 "github.com/kunalpandey1/custom-kubernetes-operator/api/v1"



It should match where you'll push the code. It doesn't have to exist on GitHub yet, but if you want others to go get it later, the path must match the real repo.

3. --project-name custom-kubernetes-operator

Question it answers: "What do I call this operator in Kubernetes?"

This name is used to build the names of the Kubernetes objects that deploy your operator:

Namespace:   custom-kubernetes-operator-system
Deployment:  custom-kubernetes-operator-controller-manager

It must be lowercase letters, digits and - only, because Kubernetes enforces that on resource names. This is the rule your folder name Kubernetes Operator broke earlier. The flag lets you override the folder name.




Don't mix these up

Thing	              Goes where	                                    Example

domain	            API group of your CRs	                          compute.cloud.com
repo	              Go imports, go.mod	                            github.com/kunalpandey1/...
project-name	      Names of the deployed operator objects	        custom-kubernetes-operator-system


What the command actually generates

From these three answers, it writes the files you saw in your project tree:

go.mod: contains the repo path
cmd/main.go: the entry point that starts the manager
config/: Kustomize YAMLs that use the project name and domain
Makefile, Dockerfile: build and deploy commands
PROJECT: a file recording your domain, repo and name, so later commands like create api know them

That's why you pass these flags once at the start. Kubebuilder saves them in PROJECT, and every later command reads them from there.

create api (done)
   ↓
edit api/v1/ec2instance_types.go   → define Spec and Status fields
   ↓
make manifests                     → turns your Go types into the CRD YAML
   ↓

Two things to know

Spec vs Status: the generated types file has Spec and Status structs with 
placeholder fields (a Foo field, for example). Replace them with your own. 
This is the CRD schema we talked about.

Version choice: v1 is fine for learning. Real projects often start 
with v1alpha1 to signal that the API may change. Changing a version 
later means adding a new one, not renaming, so it's a decision worth 
making early.






Why it's called "create api"


Yes. create api defines the API for your custom resource: the Go 
type (EC2Instance with its Spec and Status), the group, version and kind, 
and the registration that makes Kubernetes understand it. 
The CRD YAML comes later, when make manifests converts that Go type.

In Kubernetes, every resource type is an API. 
Pod is an API at /api/v1/pods, and Deployment is an API at 
/apis/apps/v1/deployments. When you add a CRD, you are adding 
a new API endpoint to the API server:

/apis/compute.cloud.com/v1/namespaces/<ns>/ec2instances

So "create api" means "add a new API (resource type) to my operator." 
It is the same idea as the "everything is an API" line from your slide.

What it actually generates

It doesn't generate the CRD yaml or a CR directly. This is the exact split:



You expected	                What actually happens

CRD	                          It generates the Go struct (ec2instance_types.go). The CRD YAML is produced later by make manifests, which reads your Go structs.
CR	                          It generates a sample CR in config/samples/, with placeholder fields. Real CRs are what users apply later.
(not mentioned)	              The controller with an empty Reconcile(), and zz_generated.deepcopy.go


So the CRD is not written by hand as YAML. You define the schema in Go and Kubebuilder converts it:

ec2instance_types.go  --(make manifests)-->  CRD YAML  --(make install)-->  your cluster

How you'd build it

You run create api once per kind:

kubebuilder create api --group network --version v1 --kind VPC

apiVersion: compute.cloud.com/v1
kind: EC2Instance
---
apiVersion: storage.cloud.com/v1
kind: S3Bucket
---
apiVersion: network.cloud.com/v1
kind: VPC

This is the same pattern as the AWS Controllers for Kubernetes 
and Crossplane projects I mentioned earlier. One project, many resource types.

One catch: multiple groups

A Kubebuilder project is single-group by default, with the 
layout api/v1/. To add a second group like storage, enable 
multigroup mode first:


kubebuilder edit --multigroup=true

The layout then becomes api/compute/v1/, api/storage/v1/, 
and so on. It's best to run this before you create your first API. 
If you already have EC2Instance in api/v1/, enabling it later means 
moving that folder and updating the imports.

Multiple kinds in the same group, like EC2Instance and a security 
group both under compute, don't need multigroup. They just share api/v1/.

KubeBuilder Architecture:- 

HA stands for high availability. It means running more than one copy 
of your operator, so if one copy crashes or its node goes down, 
another copy is already running and can take over. With only one copy, 
a crash means nothing reconciles until Kubernetes restarts it.

The problem is that two copies running at the same time would both see the 
same EC2Instance change and both call Reconcile(). Both could then ask AWS 
to create an instance, and you'd end up with duplicates or the two copies 
overwriting each other's updates.

Leader election solves this by choosing one copy to be the leader. 
Only the leader runs the controllers and reconciles resources. The other 
copies stay running as standbys and do nothing except keep checking on 
the leader.

It works through a shared object in the cluster, usually a Lease. The 
leader keeps renewing that Lease every few seconds, which tells the others 
it is still alive. If the leader crashes and stops renewing, the Lease 
expires, one of the standby copies grabs it and becomes the new leader, 
and reconciling continues with only a short pause.

In your project, this is controlled by a flag in main.go:

--leader-elect=true


Kubebuilder turns it on in the deployed manifests, which is why you'll 
see an ID like <something>.cloud.com in main.go. That's the name of the Lease. 
When you test locally with make run, you run a single copy, so leader 
election isn't needed and is off by default.

To note it down: leader election makes sure only one copy of your operator 
reconciles at a time when several are running for high availability, and if 
the leader dies, another copy takes over.

1. Client

Communicates with the API server, handling authentication and protocols.

2. Cache

Holds recently watched or fetched objects, used by controllers and webhooks. It's built on the client.

The catch is that the cache can be slightly stale. This is why the rules from your notes matter: don't trust old values, observe the world each time, and make every action idempotent. It's also why you DeepCopy() before modifying an object, so you don't corrupt the cache.

The ... boxes

3. Controller

sigs.k8s.io/controller-runtime/pkg/controller

The diagram describes it as:

One per Kind that is reconciled. Your EC2Instance gets its own controller, 
and a future S3Bucket would get another.

Owns resources created by it. If your controller creates other objects 
(a ConfigMap, a Job), it can mark itself as their owner (Owns(...)). 
Changes to those objects then trigger reconciles of the parent, and 
deleting the parent cleans them up.

Uses caches and clients, and gets events via filters.

Calls a Reconciler each time it gets an event.

Handles back-off, queuing and re-queuing. Events go into a work queue. 
If Reconcile() returns an error, the controller retries with an increasing 
delay. This is the self-healing from your sad path (return an error and 
the controller requeues).



Event → Predicate → Reconciler

This is the flow shown by the big downward arrow labelled Filter:

Event ──► Predicate (filter) ──► Reconciler

Event: something changed in the cluster, such as an EC2Instance created, 
updated or deleted.

Predicate (pkg/predicate): filters the stream of events and passes only 
those that need action to the reconciler. Without it, every tiny change 
triggers a reconcile.

This is the fix for the sad-path loop we discussed. If your controller 
writes .status, that causes an event, which triggers Reconcile again. 
A predicate such as GenerationChangedPredicate ignores events where only 
the status changed and the spec didn't, which breaks the loop.

Reconciler (pkg/reconciler): "user-provided logic is added into the reconciler.
Reconcile function." Everything else in the diagram is framework code. 
This is the one box you write: the observe, compare, act logic inside 
Reconcile() in ec2instance_controller.go.



4. Webhook

sigs.k8s.io/controller-runtime/pkg/webhook

The diagram says: zero or one webhooks, one per Kind. They're optional. 
Your operator works without any.

Webhooks sit in a different place from the controller. 
They run before an object is saved to the cluster, when a user does 
kubectl apply. The controller, by contrast, acts after the object is saved.

kubectl apply ──► API server ──► AdmissionRequest ──► Defaulter ──► Validator ──► saved

AdmissionRequest: the API server asks your webhook, "someone is 
creating or updating this object, what do you think?"

Defaulter ("sets unset fields in spec"): fills in missing values. 
If the user leaves out type, the defaulter could set type: t3.micro. 
This is called a mutating webhook.

Validator ("rejects poorly formed objects"): rejects bad input with a 
clear error. For example, if amiID is empty or doesn't start with ami-, 
the request is refused immediately. This is called a validating webhook.

For EC2Instance this is useful, because a bad AMI ID caught by the 
Validator fails right at kubectl apply, instead of failing later inside 
the controller when AWS rejects it.

How it all fits together

1. User runs kubectl apply -f ec2.yaml
2. API server calls the Webhook:   Defaulter fills gaps → Validator checks → object saved
3. Manager's Cache sees the change and sends an Event to the Controller
4. Predicate decides if the event matters
5. Controller queues it and calls Reconciler.Reconcile()
6. Your logic: observe → compare → act (calls AWS), then writes Status
7. On error, Controller retries with back-off

what happens under the hood after writing Go structs :- 



1. Build Time: Structs → CRD YAML (One-Time Setup)

The Kubernetes API server comes pre-compiled with built-in Go structs 
(like Pod and Deployment), so it already knows how to validate them. 
However, it wasn't compiled with your custom types.go code.

• When you run make manifests, a tool (controller-gen) reads your types.go 
structs and generates a CustomResourceDefinition (CRD) YAML file.

• You apply this YAML once to dynamically register your custom schema with 
the API server so it knows what fields to expect and how to validate 
incoming requests.




2. Runtime: Structs <-> JSON (The Reconciliation Loop)

When your operator is actually running in the cluster, YAML is completely out 
of the picture. Your operator's Manager and the Kubernetes API server run as 
separate processes (and likely on different nodes), 
so they cannot directly share Go memory. Instead, 
they communicate over the network via HTTP:

1. You write Go structs in controller.go (e.g., creating a Deployment struct or updating your custom resource's .Status struct).

2. Manager serializes to JSON: When you call r.Create(ctx, myDeployment) or r.Status().Update(ctx, myCustomResource), 
the manager's client converts your Go struct into JSON (using the json:"..." struct tags in types.go) and sends an HTTP POST/PUT request to the API server.

3. API Server deserializes to Structs/Map: The API server receives that JSON, validates it against the CRD schema you registered earlier, and stores it in etcd.

4. Watching works in reverse: When a user applies a YAML file for your custom resource, the API server converts it to JSON, and your operator's manager receives 
that JSON stream over an HTTP Watch connection and automatically unmarshals it back into your types.go Go struct before triggering Reconcile().

In short: YAML is only generated beforehand so the API server can learn your schema; JSON is the wire format your operator 
uses to talk to the API server over HTTP at runtime.








How request comes to operator for Reconciliation ?


1. Who converts YAML to JSON

kubectl does it, before the request is sent. The API server receives JSON 
(or protobuf) over HTTPS. It doesn't see your YAML file.

2. What the API server does

It does more than serialize. It authenticates the request, checks 
permissions (RBAC), runs the webhooks if you have any (defaulter, 
then validator), validates the object against the CRD schema, and 
stores it in etcd. The object is now saved in the cluster.

3. The API server doesn't send it to your controller

Your controller watches the API server. When your operator starts, 
its manager opens a watch connection for EC2Instance resources and 
keeps a local cache up to date. When the new object is saved, 
the API server publishes a change event on that watch. The cache sees it, 
and the event goes through the predicate and into the controller's queue.

kubectl apply (YAML → JSON)
        ↓
API server: auth → webhooks (optional) → validate → store in etcd
        ↓  (watch event)
Your operator's manager: cache → predicate → queue
        ↓
Reconcile()  →  observe, compare, act
"Controller manager"

Be careful with the name here. kube-controller-manager is Kubernetes' 
own built-in process, which runs the controllers for Pods, Deployments 
and so on. It doesn't run your code.

Your reconcile loop lives in your operator's own process, the main.go 
we went through. It has its own manager (from controller-runtime), 
either on your laptop with make run or in a Pod with make deploy. 
So a better way to say it is: the event reaches your operator's manager, 
which calls your Reconcile().





What happens under the hood when you run kubectl command ? which all processes starts ?





1. What happens when you run kubectl

Take kubectl get pods as the example. There are two halves: what runs on your machine, and what runs in the cluster.

On your machine (kubectl itself, a single process):

1. Parse the command: Cobra (the CLI library) parses the verb and flags.

2. Load kubeconfig: reads ~/.kube/config (or $KUBECONFIG) to find the current context, the API server URL, the CA cert, 
and credentials (client cert, token, or an exec plugin such as aws eks get-token).

3. API discovery: kubectl asks the server what resource types exist (/api, /apis) and caches the result in ~/.kube/cache. 
This is how it maps pods to GET /api/v1/namespaces/default/pods.

4. Build and send the HTTPS request: with auth attached. For apply/create it first validates and serializes your YAML to JSON.

In the cluster (control plane):

1. kube-apiserver handles the request in this order: authentication (who are you?), 
then authorization (RBAC: can you do this?), then admission controllers (mutating and validating webhooks, defaults, quotas), 
then schema validation. For writes it persists to etcd.

2. etcd stores the cluster state. Only the API server talks to it.

3. For reads, the API server returns the data and kubectl formats it into a table.




For writes (kubectl apply -f deploy.yaml), a chain of components reacts via watches on the API server:

1. Controller manager (Deployment controller, then ReplicaSet controller) creates ReplicaSet and Pod objects.

2. kube-scheduler sees Pods with no node assigned, filters and scores nodes, and writes the binding.

3. kubelet on the chosen node sees the Pod assigned to it and tells the container runtime (containerd or CRI-O, via CRI) 
to pull images and start containers. CNI plugins set up pod networking, and CSI handles volumes.

4. kube-proxy (or the CNI) updates Service routing rules (iptables/IPVS/eBPF).

5. Kubelet reports status back to the API server, which is what you see in kubectl get pods.


Processes in short:

Client: kubectl
Control plane: kube-apiserver, etcd, kube-scheduler, kube-controller-manager (plus cloud-controller-manager on cloud setups)
Each node: kubelet, kube-proxy, container runtime (containerd/CRI-O), CNI plugin

You can see all of this yourself with kubectl get pods -v=8 (shows the HTTP calls) or -v=6 for a lighter view.










Why we get CrashLoopBackOff Error ? 



CrashLoopBackOff is not an error in itself. It means a container starts, exits, and kubelet keeps restarting it, waiting longer 
between attempts each time (10s, 20s, 40s... capped at 5 minutes). That wait is the "BackOff".

Common causes:

Application crashes on startup: a bug, an unhandled exception, or a missing dependency.
Bad config: missing or wrong env vars, ConfigMap or Secret not mounted or wrongly keyed, bad config file.
Can't reach a dependency: the DB or another service is down or the connection string is wrong, and the app exits.
Wrong command or args: a bad command/args in the spec, or a container that runs a short task and exits (exit code 0 also causes restarts if restartPolicy: Always).
OOMKilled: memory limit too low, so the kernel kills the process (exit code 137).
Failing liveness probe: kubelet kills a healthy-but-slow container (for example, the probe fires before the app finishes starting; use a startupProbe or a longer initialDelaySeconds).
Permission problems: a non-root user can't write to a volume, a read-only filesystem, or wrong file permissions.
Wrong image or entrypoint: an architecture mismatch (arm64 vs amd64) gives exec format error.



How to debug:


kubectl describe pod <pod>            # Events, Last State, Exit Code, Reason
kubectl logs <pod>                    # current container logs
kubectl logs <pod> --previous         # logs from the crashed instance (the key one)

kubectl get events --sort-by=.lastTimestamp

1. The user makes an API call to the API server.
2. The API server first checks authentication and authorization (AA).
3. If that passes, it invokes the admission controllers, which use the three special kinds: the mutating webhook, validating admission policies, and the validating webhook.
4. The admission controllers either allow or reject the request, and the answer goes back to the user.
   If allowed, the object is saved in etcd.





Only two of the three are actually webhooks. The third, Validating Admission Policies, does the same job as a validating webhook without any webhook. All three run in the admission stage, after authentication and authorization and before the object is saved to etcd.

1. Mutating webhook: changes the request

It can modify the object before it is saved. The API server sends the object to your webhook server, and the webhook replies with the changes to make.

For your EC2Instance:

The user leaves out instanceType, and the webhook sets it to t3.micro.
It adds a default tag such as managed-by: ec2-operator.

This is the Defaulter from the controller-runtime diagram. It runs first, so that later checks see the final version of the object.




2. Validating webhook: accepts or rejects the request

It can only say yes or no. It can't change anything. The API server sends the object to your webhook server, and the webhook runs your Go code and replies allowed or denied, with a message.

For your EC2Instance:

Reject it if amiID doesn't start with ami-.
Reject it if instanceType isn't in an allowed list.
Reject an update that tries to change amiID after the instance was created.

The user sees the rejection message right at kubectl apply. This is the Validator from the controller-runtime diagram. It runs after the mutating step.





3. Validating Admission Policies: the same, without a webhook

This is a built-in Kubernetes feature that does validation without running any server. You write the rule as a small 
expression in a language called CEL inside a YAML object, and the API server evaluates it itself.


validations:
  - expression: "object.spec.amiID.startsWith('ami-')"
    message: "amiID must start with ami-"












Reconcile based on conditions:- 


It's a table of what the controller does after your Reconcile() returns, based on what you return. Your Reconcile() returns two things, a ctrl.Result and an error, and the controller checks them in priority order. The first matching level decides, and the later levels are never looked at.

The four levels

Level 1: Error
You return a non-nil error.

The Result is completely ignored, even if you set RequeueAfter in it.
The controller retries with exponential backoff: the wait gets longer after each failure (for example 5ms, 10ms, 20ms, and so on, up to a maximum of about 16 minutes). This stops a failing object from hammering the API server.
This is the self-healing path from your sad-path diagram.

return ctrl.Result{}, err

Level 2: RequeueAfter
No error, and you set RequeueAfter.

The controller runs this object again after the fixed delay you chose.
This is the forever loop he underlined. If you always return it, the object is re-checked on a timer forever.

return ctrl.Result{RequeueAfter: 60 * time.Second}, nil

Level 3: Requeue
No error, Requeue: true, and no RequeueAfter.

The controller runs it again, using exponential backoff for the delay.

return ctrl.Result{Requeue: true}, nil

Newer controller-runtime versions are phasing this flag out in favor of RequeueAfter, so it may show a deprecation warning in your version.

Level 4: Nothing
No error and no requeue flags.

The controller stops for this object. It runs again only when a new event arrives, such as the object changing.

return ctrl.Result{}, nil



You return	                                        What happens next

ctrl.Result{}, err	                                Retry with growing delays (the Result is ignored)
ctrl.Result{RequeueAfter: 60*time.Second}, nil	    Run again after exactly 60 seconds, repeatedly
ctrl.Result{Requeue: true}, nil	                    Run again with backoff delay
ctrl.Result{}, nil	                                Done. Wait for the next event.



What exponential backoff means

The delay doubles after each consecutive failure: short at first, then longer and longer. 
If something is broken, the controller retries quickly in case it was a brief problem, then slows 
down so it isn't spamming. When a run succeeds, the delay resets.
